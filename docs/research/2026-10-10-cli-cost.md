# CLI cost before considering a language port

Measured 10 October 2026 on the owner's macOS arm64 machine, Node 24.21.0,
14 logical CPUs. Source: phase 67 working tree over `9a233a9`.
[Raw observations](../evidence/2026-10-10-cli-cost.json) retain statuses,
individual timings, overlap, incomplete indicators and load context.

## What the measurements say

Ten interleaved uninstrumented/profiled fresh processes per local command,
no warmup discard. Medians in milliseconds; each column is independently
aggregated and must not be added as though it described one invocation.

| Command | Normal elapsed | Profiled elapsed | Spawn to profiler ready | CLI imports (nested in residual) | Subprocess busy | Local residual |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `--agent-help` | 50.5 | 63.9 | 51.4 | 7.0 | 0 | 9.5 |
| `status --json` | 88.5 | 99.6 | 54.6 | 7.2 | 0 | 42.1 |
| `next --json` | 71.7 | 83.2 | 44.7 | 6.2 | 0 | 34.7 |
| `time --weeks 8 --json` | 281.1 | 300.7 | 48.1 | 6.1 | 0 | 248.2 |
| `--version --json` | 50.4 | 59.6 | 37.8 | 5.0 | 13.3 | 6.1 |

Every paired invocation exited 0. These local commands made no observed
direct network calls. `--version` exercised actual Git subprocesses.
The profiler added roughly 9–20 ms to these median elapsed times; that is
an observation under this load, not an overhead constant to subtract.

Three successful real `doctor --github --json` samples had **1,727 ms** median
profiled elapsed time: **1,467 ms** subprocess busy, of which **1,440 ms** was
inside network-capable `gh`; local residual was **242 ms**, spawn-to-preload
**46 ms**, imports **6 ms**. There were two `gh` calls per sample. These are
opaque subprocess durations, not pure network latency. One nonzero child
status occurred per sample while the overall doctor exited 0; subprocess
failure counts are not the command's semantic verdict.

A separate public GitHub HTTPS metadata probe exercised direct network
instrumentation: three HTTP 200 responses, median request-through-response-end
**244 ms** (range **239–347 ms**). This was a small independent probe, not a
Keel command or a substitute for the `gh` measurements. Its duration includes
DNS/TLS/client/server work; it does not isolate the wire.

## Interpretation and limits

There is a measurable startup floor for tiny commands, but CLI imports were
only about 5–7 ms in the paired sample. `time` spent most of its time in local
residual work; determining CPU versus filesystem/scheduling cost needs a CPU
profile or finer spans. The remote doctor spent most of its time inside
`gh`. Porting Keel cannot be assumed to remove that cost.

One-minute load averages were **23.8 → 21.3** during paired measurements,
**39.4 → 36.7** during the GitHub run, and about **97** during the direct
network probe. Filesystem and network caches were uncontrolled. These are
fresh processes on a busy machine, not cold-machine benchmarks or a basis
for regression thresholds. The early exploratory baseline ranged from load
9 to 38 and is not used for a before/after speedup claim.

Per invocation, the measured accounting identity is:

`spawn-to-preload + observed-busy-union + local-residual = child-until-exit`

`observed-busy-union = subprocess-busy + direct-network-busy − overlap`

Imports are already inside that accounting. Parent elapsed additionally
includes process teardown/pipe closure. No instrumentation observes worker
threads, child internals, raw sockets or fetch body consumption; local
residual includes those gaps. This work makes no Rust/Go speedup claim and
does not change runtime performance deliberately.

## Reproduce

Use new output filenames on every run:

```sh
node scripts/profile-benchmark.mjs --output /tmp/keel-local.json --samples 10 --json
node scripts/profile-benchmark.mjs --output /tmp/keel-github.json --samples 3 --github --json
node scripts/profile.mjs --output /tmp/keel-time.json -- time --weeks 8 --json
node scripts/profile.mjs --output /tmp/keel-version.json -- --version --json
```

The paired measurement used the exported runner, alternating normal and
profiled commands with these arguments and retaining every result:

```js
import { runProfile } from './scripts/profile.mjs';
import { spawnSync } from 'node:child_process';
const cases = [ ['--agent-help'], ['status', '--json'], ['next', '--json'],
  ['time', '--weeks', '8', '--json'], ['--version', '--json'] ];
for (const args of cases) for (let i = 0; i < 10; i++) {
  const start = performance.now();
  const plain = spawnSync(process.execPath, ['bin/keel.mjs', ...args],
    { stdio: 'ignore', timeout: 60_000 });
  const plainMs = performance.now() - start;
  const profiled = await runProfile(args, { stdio: 'ignore' });
  console.log(JSON.stringify({ plainMs, code: plain.status, signal: plain.signal, profiled }));
}
```

The independent network probe used `https.get` against the public
`https://api.github.com/repos/dalmaer/keel` endpoint, a `User-Agent` header,
15-second socket timeout with request destruction, and `response.resume()`
through `end`, requiring HTTP 200. A temporary `.mjs` entry was passed to
`runProfile([], {entry, stdio: 'ignore'})` three times. No credentials,
request/response content or command output were saved in the timing record.

## A failed measurement retained

The initial GitHub benchmark exited 1 before making any network call. New
JSDoc object types used double braces, which the practice renderer interpreted
as placeholders. Spacing the type braces fixed the integration, and a new
test checks that the actual renderer preserves every checked source byte.
Those failed observations remain in the raw record and are excluded from
successful-command estimates; they do not count as a fast GitHub path.
