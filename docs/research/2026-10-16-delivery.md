# Delivery: a change reaches production once, checked

The owner, 2026-10-16: "I ask for something to be changed. I ask for something
else to be changed. The first one comes back and starts to run all of the tests
and kick off the path to build, test, deploy, promote. The second one comes back
and … now there are two items doing the heavy work of a full test path." Then:
look at keel, isocan (which has a promote step) and ledger for what is common
and what is a configurable difference, and spec it.

This note is that comparison and the five phases that follow from it. It was
written from read-only surveys of keel (`ae7febb`), isocan (`7ffdb7e`) and
ledger (main), all on 16 October 2026.

## What each project does today

| | keel | isocan | ledger |
| --- | --- | --- | --- |
| Gate on PRs and main | `check.yml`, cancels per ref | `pr.yml` 4 shards, cancels per branch; `release.yml` on main, 4 more shards, no cancelling | `test.yml`, cancels per ref; the suite twice (+400 days); web build |
| Doc-only skip | no | no | `ci-scope.mjs` |
| Tested ref | none | `green`, moved by a serialised publish | none |
| Deploy | none | Cloud Build on `green` (dev) | `deploy.yml` on every push, queued, never cancelled |
| Skip what is live | none | `release-order.sh` skips superseded commits | diff against the live SHA from `/api/version` |
| Promote | none | a person moves the `prod` tag; nothing checks it names `green` | none; main is production |
| Verify production | none | a manual curl (docs disagree: `/healthz` vs `/api/healthz`) | `verify-production.mjs` and `verify-deploy.yml`, push alert |
| Alert | GitHub's mail | GitHub's mail | `ci-alert.yml` to Telegram |
| Required checks, merge queue | none | none | none |

## Where the expensive path runs more than once

- A PR runs the full suite and main runs it again after merge (isocan 4 + 4
  shards), with nothing reused.
- Local and CI repeat each other: ledger's pre-push `check:code`, the
  conductor's `check:all`, then CI; isocan's conductor `test:deep`, then
  `release.yml`.
- Keel's own passes each run the full gate (night, loop, climb, tend, robot),
  and their PRs get no CI or run it again.
- Ledger deploys in parallel with its tests, so a red suite reaches production
  and is caught after.
- Two sessions can each run the full gate and push; only the conduct skill's
  wording ("never run a build beside another build") stands in the way.
- Ledger's CI runs the test ledger and keeps none of its output, so the night's
  test history is empty there.

## What is common, and proven somewhere

1. **Verify in parallel, publish one at a time, skip the superseded** (isocan's
   `release-order.sh`): many commits test at once; one queued publisher
   advances a tested ref, only for the newest green commit, and skips a commit
   a later one has passed. This is the owner's "one builder does the expensive
   path".
2. **A tested ref deploys follow** (isocan's `green`): production is never
   "whatever is on main".
3. **Skip a deploy production already has** (ledger's live-SHA diff).
4. **Production serves the commit** (ledger's `verify-production.mjs`,
   `watch-deploy.ts`; isocan's healthz with a commit): after a deploy, wait
   until production reports the commit or a descendant, then smoke-test.
5. **Promote is a guarded gesture**: move a production ref only to a tested
   commit, then verify (isocan's tag move, with the guard it lacks).
6. **Tests cancel the superseded; deploys never cancel** (ledger has both),
   checked by a workflow test (isocan's `workflows.test.ts`).
7. **Doc-only changes skip the suite** (ledger's `ci-scope.mjs`).
8. **One alert on failure**, where the owner already looks (ledger's
   `ci-alert`; keel's morning issue and board).
9. **One gate result per commit, shared**: keel's night already reuses CI's
   result for an exact commit; the judges, loop and pre-push do not.

## What differs, and becomes configuration

```json
"delivery": {
  "gate":    "npm run check:all",
  "shards":  4,
  "tested":  "green",
  "deploy":  "vercel deploy --prod | a Cloud Build trigger on the tested ref | none",
  "version": "/api/version",
  "promote": "tag:prod | none",
  "smoke":   ["/", "/.well-known/oauth-authorization-server"],
  "alert":   "morning | telegram"
}
```

Keel owns the order and the checks (gate, one publisher, deploy from the tested
ref, verify, promote, alert). Each project keeps its own deploy mechanism.
Project-specific pieces stay in the project: isocan's emulator and Java setup,
ledger's data repo and +400-day pass, Vercel's quota workaround, Cloud Run's
infra.

## Rules

- A bot never writes to `main`; the publisher moves only the tested ref.
- Production moves only to a commit the gate passed, and a deploy is verified
  by what production reports, not by the deploy command's exit code.
- Promotion stays a person's gesture where a project has one; keel guards it,
  never automates it.
- A deploy is queued, never cancelled; a test run may be cancelled by a newer
  commit on the same ref.

## The phases

| Phase | Title | Depends on |
| --- | --- | --- |
| 79 | One gate result per commit, shared by every pass | 33, 15 |
| 80 | Changes are verified in parallel and published one at a time | 79 |
| 81 | Production is checked by the commit it serves | 80 |
| 82 | Promotion is a guarded gesture | 81 |
| 83 | Agent sessions hand a change off as ready, and one integrator runs the expensive path | 80, 70 |

79 first: every later phase reads a commit's gate result instead of running the
gate again. 80 is the core of the owner's ask. 83 changes how sessions work
(the conduct skill and claims), so it lands after the machinery it hands off to.

## Open

- **A merge queue instead of a tested ref.** GitHub's merge queue batches and
  bisects merges, but the fleet mostly pushes straight to main (ledger: 2 merges
  in its last 42 commits). A tested ref works for both; a queue is an option a
  project may add.
- **Sharding** is isocan's; keel records shard count as configuration and
  leaves the balancing to the project in this round.
- **Alerts beyond the morning issue** (Telegram) stay a project's own until
  asked for.
