# Keel: design

**Written 2 October 2026.** What keel is, the mechanisms it needs, and the
debt each one discharges. The phases in [`phases/`](phases/) are the walk;
this page is the argument they cite. [The fleet survey](research/2026-10-02-the-fleet.md)
is the evidence it was drawn from.

## The problem, in one paragraph

Four projects run the same way of working: isocan, ledger, duo and cajones (ritmo).
None of them got it from a shared source. Each one copied it by hand from the one before:

> isocan → ledger ("adapted from isocan") → duo ("ported from ledger, which
> ported it from isocan") and cajones ("adapted from Ledger's phase workflow").

Every copy is a fork that can't hear from the original. Here is what that costs:

- ritmo's roadmap generator checks evidence and dependencies; ledger's doesn't.
- duo's lessons carry `(ledger 6)` citations by hand.
- On the day keel started, isocan made its conduct skill much cheaper to run (`7227f325`). No other project would ever have heard about it.
- isocan's own untracked second copy of that skill was already twelve days stale.

Status written in two places drifts. That is lesson 1 of every one of these
repos, and keel exists because the *practice itself* is now written in four.

## What keel is

Keel is the source of a practice, a CLI that installs and updates it, and a
place where lessons from the projects using it get collected and turned into
the next version.

- **The practice** is a set of *practices*. Each one is a bounded way of
  working with a failure it prevents. Each lives in `practices/<name>/`:
  - its argument (`README.md`: the failure, the rule, where it came from);
  - the files it installs;
  - the checks that enforce it;
  - its migrations.
- **A project** that keel manages carries `.keel/keel.json`. It names the
  project, its repo, the practice version it is on, and the practices it
  has switched on.
- **The CLI** (`keel`) is how a person or an agent acts on either side. On a
  project it can `init`, `adopt`, `update`, `doctor`, `improve`, `goal`, `next`
  and `lessons`. On keel itself it can `learn`, `release` and `fleet`.

Keel runs on itself. Its own `.keel/keel.json` says `"keel": "self"`, its
roadmap is generated by the same script it will ship, and every practice is
proved on keel before any other project gets it.

## The mechanisms

### 1. Practices, and who owns each file (phases 1, 5)

A file keel puts in a project is one of three kinds. Getting the boundary
right is what makes `update` possible at all.

| Kind | Example | On update | Local edit means |
| --- | --- | --- | --- |
| **managed** | `scripts/roadmap.mjs`, `.agents/skills/conduct/SKILL.md`, workflows | Overwritten. Header says so. | Drift. `doctor` flags it; `lessons` offers it upstream. |
| **block** | the `<!-- keel:begin … -->` regions of `AGENTS.md` | The region is re-rendered; the rest of the file is the project's. | Same as managed, for the region only. |
| **seeded** | phase files, `docs/lessons.md`, `docs/goals.json` | Never touched. Migrations may *transform* it, with a diff. | Nothing; the project owns it. |

`.keel/lock.json` records the hash each managed file and block was written
with, so drift is a fact rather than a guess. **A local edit to a managed file
is the most valuable signal keel gets**: someone needed the practice to be
different. `doctor` must never just revert it.

### 2. One file, many doorways (phase 1)

From isocan, who learned it first: a skill lives once, under
`.agents/skills/<name>/`. Claude Code reaches it through a committed symlink,
`.claude/skills/<name>`. `CLAUDE.md` is one line pointing at `AGENTS.md`.
Keel never writes a second copy of an instruction into another harness's
directory. A copy is a fork that can't hear updates.

### 3. Versions and migrations (phase 6)

Keel is released as a practice version. Each version is a git tag on keel.
`migrations/NNNN-name.mjs` exports two things:

- `applies(project)`, which must be idempotent;
- `up(project)`, which returns the edits as a list rather than making them.

`keel update` runs in this order, and the order matters:

1. **Update the CLI itself first.** An old CLI must never run a new migration.
2. Run each pending migration. Stop at the first one that can't apply cleanly.
3. Re-render the managed files and blocks for the new version.
4. Run the project's `check`.
5. Bump `practice` in `.keel/keel.json`.
6. Open a PR (or leave a working-tree diff with `--local`). A practice change
   lands like any other change: read by a person, checked by CI.

### 4. Lessons flow both ways (phases 7, 8)

**Upstream (`keel lessons`, run in a project).** It gathers three things:

- new rows in the project's `docs/lessons.md`;
- drifted managed files;
- *practice-shaped* commits. These are commits that touch `AGENTS.md`, skills,
  or workflows, exactly the kind of commit `7227f325` was.

Each one is filed as an issue on `dalmaer/keel`, labelled `lesson`, with a
fingerprint so it is filed only once. Lessons are shapes, not incidents: the
issue carries the shape, what it cost, and the guard. That is the same
three-column form every one of these repos already uses.

**At home (`keel learn`, run on keel).** It reads open `lesson` issues and
also polls **sources**. A source is an upstream file a practice was adapted
from, pinned to a commit. Isocan's conduct skill is the first one.

For each item it **proposes** one of four things, with a reason:

- a central lesson;
- a practice change, plus the migration that carries it to projects;
- "project-specific, decline";
- "already a shape we have, link it".

**An agent proposes; a person decides.** That split comes from ledger's Loop
triage, because a decision here changes every project's practice. Accepted
proposals become a release.

### 5. Goals over phases (phase 9)

Goals are outcomes, not dates. They are ritmo's milestones, renamed because
"goal" is the word people use.

- `docs/goals.json` lists them.
- Each phase names its goal.
- Goal progress is derived, never stored.
- `keel goal add|list|show|retire` edits the file.

`keel next` gives the first unfinished phase in number order whose
dependencies are built, and its *Next action*.

### 6. The night shift (phases 10, 11)

The rules come from isocan's "night shift's pull requests", and each one was
paid for:

- **Measure before anything tries to fix.** Deterministic numbers first, a
  model's opinion last.
- **A bot writes a pull request, never to `main`.**
- **A workflow's queue never holds more than one open PR, the newest**, and
  machinery enforces that, not a person remembering.
- **A merge is checked, not trusted.** A `GITHUB_TOKEN` PR never runs CI, so
  the merge step runs the suite itself.
- **A guard must fire into a room someone is in.** A red nightly is a failed
  workflow GitHub emails about. It is never a page nobody opens.

Keel installs the following, all managed:

- `check.yml`
- `keel-night.yml`, which runs `keel improve --report` and opens one PR with a
  dated health page
- `claude.yml` (`@claude` on issues; it opens PRs, a person merges)
- Renovate's lanes: daily patch/minor automerge on green, Monday lockfile,
  Monday majors for a person, Node on its own
- a weekly `keel-update.yml` that opens the practice-update PR

`keel improve` is the eval half. It answers "is the practice actually
working here?" with numbers:

- Is CI red, and for how many commits?
- Is the roadmap stale?
- Which phases are unfinished with no issue?
- Which lessons have no named guard?
- How many machine PRs are queued?
- How old are the dependencies?
- How much do managed files drift?
- Has the deploy been verified?
- What did conducting cost, from the subagent-time measure isocan built for
  `7227f325`?

It writes a page. It proposes one change. It never makes it.

### 7. The fleet (phase 12)

`fleet.json` on keel lists the projects keel manages. `keel fleet` reads each
project's `.keel/keel.json` and its last health page through `gh`. It answers
three questions:

- Which projects are behind on the practice?
- Which are red?
- Which have lessons we haven't heard?

## Rules keel holds itself to

- **Zero runtime dependencies, Node ≥ 24, no build step.** Installing from
  `main` must work. isocan #47 was an install from an unbuilt branch that
  shipped an empty directory.
- **Every command takes `--json`.** Agents drive keel; they never parse prose.
- **`keel --agent-help` is the agent's cold start, and ships with the CLI.**
  Upgrading the CLI upgrades the instructions. A test fails when a verb isn't
  in it (isocan's surface test).
- **⚑ steps are asked, with the price.** Creating a GitHub repo, setting a
  secret, enabling Pages, and spending model tokens on a schedule all wait
  for a yes.
- **Never invent evidence.** A planned feature is not an implemented one. A
  scripted run is not a person's use.

## Deliberately open

- **How the CLI is installed.** The options are `npm i -g github:dalmaer/keel`,
  a clone at `~/.keel` that `keel` pulls, or a published package. This settles
  in phase 2. The constraint is that `update` must be able to update the CLI
  before anything else.
- **Whether isocan is adopted.** isocan is Dimitri's repo. Keel can *learn*
  from it as a source without managing it. Adopting it is his decision, not keel's.
- **Stitch Loop and the isocan canvas.** Both are optional practices. They
  come in once two projects have used them through keel, not before.
- **License.** keel adapts Apache-2.0 material from isocan, with attribution in
  each file. Keel's own license is the owner's call.
