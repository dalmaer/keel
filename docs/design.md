# Keel: design

**Written 2 October 2026.** What keel is, the mechanisms it needs, and the
debt each one discharges. The phases in [`phases/`](phases/) are the walk;
this page is the argument they cite. [The fleet survey](research/2026-10-02-the-fleet.md)
is the evidence it was drawn from.

For commands and flags, use the [task guides](../README.md#guides) or
`keel --agent-help <topic>`. Dated decisions below retain their original context.

## The problem, in one paragraph

Four projects run the same way of working: isocan, ledger, duo and cajones (ritmo).
None of them got it from a shared source. Each one copied it by hand from the one before:

> isocan → ledger ("adapted from isocan") → duo ("ported from ledger, which
> ported it from isocan") and cajones ("adapted from Ledger's phase workflow").

Every copy is a fork that can't hear from the original. Here is what that costs:

- ritmo's roadmap generator checks evidence and dependencies; ledger's doesn't.
- duo's lessons carry `(ledger 6)` citations by hand.
- On the day keel started, isocan made its conduct skill much cheaper to run (`7227f325`). No other project would ever have heard about it.
- isocan's own untracked second copy of that skill was already twelve days stale.

Status written in two places drifts. That is lesson 1 of every one of these
repos, and keel exists because the *practice itself* is now written in four.

## What keel is

Keel is the source of a practice, a CLI that installs and updates it, and a
place where lessons from the projects using it get collected and turned into
the next version.

- **The practice** is a set of *practices*. Each one is a bounded way of
  working with a failure it prevents. Each lives in `practices/<name>/`:
  - its argument (`README.md`: the failure, the rule, where it came from);
  - the files it installs;
  - the checks that enforce it;
  - its migrations.
- **A project** that keel manages carries `.keel/keel.json`. It names the
  project, its repo, the practice version it is on, and the practices it
  has switched on.
- **The CLI** (`keel`) is how a person or an agent acts on either side. On a
  project it can `init`, `adopt`, `update`, `doctor`, `improve`, `goal`, `next`
  and `lessons`. On keel itself it can `learn`, `release` and `fleet`.

Keel runs on itself. Its own `.keel/keel.json` says `"keel": "self"`, its
roadmap is generated by the same script it ships, and every practice is
proved on keel before any other project gets it.

## Project lifecycle on isocan (in progress, 8 October 2026)

[The project canvas specification](specs/isocan-project-canvas.md) defines
one isocan canvas per Keel project: goals and delivery, Loop, lessons, retros,
health, upkeep and evidence, with source-linked measures of fixes and improvement.
It reuses the existing readers, reconciliation and night reports. The canvas
is a projection; source files and GitHub keep their respective authority.
[Phase 50](phases/50-project-life-on-isocan.md) tracks implementation and the
real-project walk. Local snapshot/render and reviewed retro capture work now;
the optional public-CLI adapter publishes immutable runs. Conditional updates,
the stable live pulse and the deployed owner walk remain unproven. See the
[current command guide](guide/project-canvas.md) for supported behavior.

## The mechanisms

### 1. Practices, and who owns each file (phases 1, 5)

A file keel puts in a project is one of three kinds. Getting the boundary
right is what makes `update` possible at all.

| Kind | Example | On update | Local edit means |
| --- | --- | --- | --- |
| **managed** | `scripts/roadmap.mjs`, `.agents/skills/conduct/SKILL.md`, workflows | Overwritten. `.keel/lock.json` records that keel wrote it. | Drift. `doctor` flags it; `lessons` offers it upstream. |
| **block** | the `<!-- keel:begin … -->` regions of `AGENTS.md` | The region is re-rendered; the rest of the file is the project's. | Same as managed, for the region only. |
| **seeded** | phase files, `docs/lessons.md`, `docs/goals.json` | Never touched. Migrations may *transform* it, with a diff. | Nothing; the project owns it. |

`.keel/lock.json` records the hash each managed file and block was written
with, so drift is a fact rather than a guess. Managed files carry **no
header** (decided 2 October, phase 5). A header would change every managed
file's bytes, and the lock says it better; a file adapted from upstream
keeps its one provenance comment. **A local edit to a managed file
is the most valuable signal keel gets**: someone needed the practice to be
different. `doctor` must never just revert it.

### 1a. Adopting a project that already has a version of the practice (phase 4)

Found by reading duo and cajones on 2 October, before adopt existed:

- **The check command differs.** ritmo's `check` is a syntax check; its gate is
  `check:all`. duo's `check` also typechecks and builds.
- **The phase files differ.** duo's built phases carry no evidence and only two
  of keel's six sections.

So `adopt` follows two rules:

- **The project's gate is config, not an assumption.** `.keel/keel.json` gets
  a `check` field (default `npm run check`), and keel's workflows run that.
- **A practice is switched on only where the project already satisfies it.**
  Where it doesn't, adopt records it as a *local variant* in `.keel/keel.json`,
  with a proposal for how to converge, and installs nothing for it. Adopt
  never rewrites a project's phases into a shape their history can't support,
  and never invents evidence to make a built phase pass. A local variant can
  converge later through a migration the owner accepts.

### 2. One file, many doorways (phase 1)

From isocan, who learned it first: a skill lives once, under
`.agents/skills/<name>/`. Claude Code reaches it through a committed symlink,
`.claude/skills/<name>`. `CLAUDE.md` is one line pointing at `AGENTS.md`.
Keel never writes a second copy of an instruction into another harness's
directory. A copy is a fork that can't hear updates.

### 3. Versions and migrations (phase 6)

Keel has two versions: `package.json` and the release tag identify the CLI;
`practices/VERSION` identifies what projects receive. The practice version
moves only when practices, migrations or `docs/lessons.md` change. A CLI-only
release leaves projects current (the phase 22 decision is recorded below).
`migrations/NNNN-name.mjs` exports two things:

- `applies(project)`, which must be idempotent;
- `up(project)`, which returns the edits as a list rather than making them.

`keel update` runs in this order, and the order matters:

1. **Update the CLI itself first.** An old CLI must never run a new migration.
2. Run each pending migration. Stop at the first one that can't apply cleanly.
3. Re-render the managed files and blocks, bump the lock and `practice` in
   `.keel/keel.json`, and regenerate the roadmap.
4. Run the project's `check` on that tree. On failure, restore every byte
   update touched.
5. Open a PR (or leave a working-tree diff with `--local`). A practice change
   lands like any other change: read by a person, checked by CI.

### 4. Lessons flow both ways (phases 7, 8)

**Upstream (`keel lessons`, run in a project).** It gathers three things:

- new rows in the project's `docs/lessons.md`;
- drifted managed files;
- *practice-shaped* commits. These are commits that touch `AGENTS.md`, skills,
  or workflows, exactly the kind of commit `7227f325` was.

Each one is filed as an issue in the configured inbox, labelled `lesson`, with a
fingerprint so it is filed only once. Lessons are shapes, not incidents: the
issue carries the shape, what it cost, and the guard. That is the same
three-column form every one of these repos already uses.

**At home (`keel learn`, run on keel).** It reads open `lesson` issues and
also polls **sources**. A source is an upstream file a practice was adapted
from, pinned to a commit. Isocan's conduct skill is the first one.

For each item it **proposes** one of four things, with a reason:

- a central lesson;
- a practice change, plus the migration that carries it to projects;
- "project-specific, decline";
- "already a shape we have, link it".

**Private projects go home privately** (decided 4 October, phase 21). keel
is public, and some projects aren't. Lesson issues go to a private inbox
repo named in keel's config, and proposals and decisions stay on its
issues. Only what the owner accepts, written in general terms, reaches
keel's public lessons table.

**An agent proposes; a person decides.** That split comes from ledger's Loop
triage, because a decision here changes every project's practice. Accepted
proposals become a release.

### 5. Goals over phases (phase 9)

Goals are outcomes, not dates. They are ritmo's milestones, renamed because
"goal" is the word people use.

- `docs/goals.json` lists them.
- Each phase names its goal.
- Goal progress is derived, never stored.
- `keel goal list|show` reads goals; `add|retire` edits the file.

`keel next` gives the first phase left to build in number order whose
dependencies are satisfied, and its *Next action*. Built, lived-in and
partial phases marked `owes: walk` satisfy dependencies; a phase owing
only a walk is skipped, as are superseded phases and retired goals.

### 6. The night shift (phases 10, 11)

The rules come from isocan's "night shift's pull requests", and each one was
paid for:

- **Measure before anything tries to fix.** Deterministic numbers first, a
  model's opinion last.
- **A bot writes a pull request, never to `main`.**
- **A workflow's queue never holds more than one open PR, the newest**, and
  machinery enforces that, not a person remembering.
- **A merge is checked, not trusted.** A `GITHUB_TOKEN` PR never runs CI, so
  the merge step runs the suite itself.
- **A guard must fire into a room someone is in.** A red nightly is a failed
  workflow GitHub emails about. It is never a page nobody opens.

**Projects run on their own** (settled 3 October, phase 15, on the owner's
word). A project's workflows never reach back to keel at runtime: no keel
checkout, no keel token. Everything a workflow runs ships *into* the project
as managed files, the way `scripts/roadmap.mjs` already does. Keel is the
source of the practice, the channel that carries changes out to projects, and
the place lessons come home to. Changes go out from keel: `keel fleet update`
opens the update PR in each project that is behind. A project never pulls
keel.

Keel installs the following, all managed:

- `check.yml`
- `keel-night.yml`, which runs the project's `scripts/keel/improve.mjs --report`
  and opens one PR with a dated health page
- `claude.yml`, when the optional `claude` practice is enabled (`@claude` on
  issues; it opens PRs, a person merges)
- Renovate's lanes: daily patch/minor automerge on green, Monday lockfile,
  Monday majors for a person, Node on its own
- *(retired in phase 15)* a weekly `keel-update.yml` in each project. Updates
  go out from keel instead, via `keel fleet update`.

`keel improve` is the eval half. It answers "is the practice actually
working here?" with numbers:

- Is CI red, and for how many commits?
- Is the roadmap stale?
- Which phases are unfinished with no issue?
- Which lessons have no named guard?
- How many machine PRs are queued?
- How old are the dependencies?
- How much do managed files drift?
- Has the deploy been verified?
- What did conducting cost, from the subagent-time measure isocan built for
  `7227f325`?

It writes a page. It proposes one change. It never makes it.

### 7. The fleet (phase 12)

`fleet.json` on keel lists the projects keel manages. `keel fleet` reads each
project's `.keel/keel.json` and its last health page through `gh`. It answers
three questions:

- Which projects are behind on the practice?
- Which are red?
- Which have lessons we haven't heard?

### 8. Reconcile records with delivery and decisions (phase 26)

**Implemented 4 October 2026 as the optional `reconciliation` practice.**
Ledger PRs #22 and #38 exposed
three recurring gaps: merged work still called draft, completed work still
named as next, and superseded architecture still presented as current.
[The reconciliation practice design](research/2026-10-04-reconciliation-practice.md)
assigns GitHub the merge facts, phase files acceptance and remaining work,
and decision records architecture. Implemented, merged, production-verified
and lived-in are separate claims; a merge never establishes acceptance.

PRs declare affected phases and decisions and update their records, next
actions and superseded plans. Doctor, CI record checks, improve and the
existing PR/nightly workflows share contradiction checks and reviewed
correction proposals. Keep historical evidence and local phase formats;
generate views from their owners, without another tracking system.

## Rules keel holds itself to

- **Zero runtime dependencies, Node ≥ 24.21.0, no build step.** Installing from
  `main` must work. isocan #47 was an install from an unbuilt branch that
  shipped an empty directory.
- **Every command takes `--json`.** Agents drive keel; they never parse prose.
- **`keel --agent-help` is the agent's cold start, and ships with the CLI.**
  Upgrading the CLI upgrades the instructions. A test fails when a verb isn't
  in it (isocan's surface test).
- **⚑ steps are asked, with the price.** Creating a GitHub repo, setting a
  secret, enabling Pages, and spending model tokens on a schedule all wait
  for a yes.
- **Never invent evidence.** A planned feature is not an implemented one. A
  scripted run is not a person's use.

## Deliberately open

- **How the CLI is installed.** **Settled 2026-10-02 (phase 2):** a checkout
  and `npm install -g` of it. Self-update is a `git pull` of that checkout.
  Once keel is public (phase 17), a plain `git clone` works; until then it's
  `gh repo clone`.
- **Whether isocan is adopted.** isocan is Dimitri's repo. Keel can *learn*
  from it as a source without managing it. **The owner wants it shared
  (3 Oct):** keel goes public (phase 17), and isocan's adoption is prepared as
  a PR for Dimitri (phase 16). Merging it is his decision, not keel's.
- **Stitch Loop.** **Settled 2026-10-02:** an optional `loop` practice
  (phase 14, under the night shift). It is ported from ledger's
  `scripts/loop.ts` and isocan's `scripts/loop.mjs`, and keeps their rules:
  the ranking is ours, an agent proposes, a person decides. The owner decided
  it rather than waiting for two projects to have used it through keel.
- **The practice version is the package version.** Found 4 October: a
  release made only for keel-side changes (fleet, learn) would mark every
  project behind and have `fleet update` open PRs that change nothing but a
  number. Until the two are separated, a keel-side-only change isn't
  released: it reaches users when keel's checkout is pulled. The likely fix
  is a practice version that moves only when `practices/` or `migrations/`
  change, so `keel release` refuses, or skips the bump, when they haven't.
  **Settled 2026-10-04 (phase 22):** two versions. The CLI's is
  `package.json` and the release tag; the practice's is `practices/VERSION`,
  the one file every reader goes through. `keel release` always bumps the
  CLI, and bumps the practice only when `practices/` or `migrations/` differ
  from the last practice release (the last commit that changed
  `practices/VERSION`, else its tag); the WHATSNEW entry says which kind it
  was, and `keel update` carries only practice entries. What settled it: the
  dry run of a release after 0.5.2, whose changes were all keel-side, now
  reports the practice unchanged at 0.5.2 and leaves every project current.
- **The isocan canvas.** Still an optional practice that comes in once two
  projects have used it through keel, not before.
- **License.** **Settled 2026-10-03:** Apache-2.0, matching isocan, chosen when
  the owner decided keel goes public (phase 17). Adapted isocan material keeps
  its attribution in each file.
