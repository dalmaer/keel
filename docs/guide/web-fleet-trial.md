# Try looking after your plates from the web

This is the phase108 owner worksheet. Use it with the
[visual tour](web-tour.md), [operation coverage guide](web-operation-experience.md)
and [deployment/restore worksheet](web-recovery.md). It records a real trial;
it is not evidence that a trial already happened.

Select the projects, participants, physical phone/desktop, private evidence
location and observation window first. Record the exact serving deployment and
source revisions. Review each operation's current access, activated storage,
worker/model support and approved allowance. A local implementation or a green
test does not enable hosted execution. No step below grants new permissions,
provider spending, repository access or a backup destination.

## Start from Home

On the phone, open Home and find a decision, a guided test and a recent addition.
Switch to each selected project and back to All plates. Follow source links and note
stale or unavailable coverage. Keep a card open while a refresh becomes available;
check that you can review it before adopting new data. Repeat on desktop using
the same records. Record where you needed a terminal or could not find a next
action; do not count that journey as fully operable from the web.

Save private screenshots only to the approved private capture store or evidence
destination. Record their revision and provenance. Use the screenshot and preview
links in the visual tour to orient yourself; synthetic screenshots are not
evidence about your own project.

## Walk the operating journeys

| Journey | What to do | What to record |
| --- | --- | --- |
| Decision and guided test | Review exact source/diff, record a decision, then a test that works and one that fails or cannot be tested | Source revision, original receipt, your actual steps/result and repair follow-up; acceptance remains a separate reviewed action |
| Failed night | Inspect one failed run, its attempt, stages, evidence and cost coverage | Actual cause, source timestamp, missing logs, native retry eligibility and expected effects |
| Approved retry | Review and run only the supported registered retry within its approved allowance; reconnect after submission | Original request/parent attempt, exactly one dispatch, resulting provider attempt, observed outcome and retained unknowns |
| Routine worker | Inspect a supported routine, request bounded work, and inspect a lost callback or interrupted connection | Original request/run identity, reserved minutes, worker/provider state, cancellation request versus confirmation |
| Learning | Trace a lesson to its source and decision; review exact audience before any approved publication | Private/public destination, source evidence, accepted/released/observed-adoption states separately |
| Canary update | Preview one approved project, inspect preparation/check output and the exact proposed PR | Target revision, preserved project files, checks, PR identity and partial rollout state; a PR is not an observed install |
| Observed version | After the separately approved delivery step, refresh the project version | CLI/practice/lock versions and freshness; merged and installed remain separate |
| Capacity and fallback | Inspect pool, units, source age and task policy; preview an approved fallback inside its budget | Why the preferred model was ineligible, allowed alternative, privacy/data scope, exact quote and held allowance |
| Checkpoint continuation | Only for a supported terminal first stage, review its retained output and next-stage preview | Owner decisions, source revision, remaining task allowance and new attempt identity; no live context swap |
| Saved draft and reconnect | Explicitly save a private draft, leave/reopen it, and reconnect after session expiry | Save confirmation/version, current source comparison and fresh preview; unsaved/offline edits can be lost |

Current support is deliberately bounded. Read each screen's capability reason.
Unknown subscription quotas are not invented, and model metadata is not a quota
read. A disabled or unsupported routine is a gap to record, not an invitation to
run arbitrary shell commands through the app.

## Exercise failures without inventing success

Use an approved isolated trial or an owner-approved reversible change. Record
expected and observed outcomes separately for each case:

| Case | Required observation |
| --- | --- |
| Removed scope or expired credential | Old access fails; fresh authorization does not reveal an unauthorized project |
| Stale capacity or exhausted allowance | New work refuses or waits with a supported reason; unknown usage never becomes zero |
| Duplicate click or reconnect after lost response | Inspect the original request; no second external effect |
| Worker loss or missing callback | Unknown execution remains unresolved and charged until trustworthy evidence settles it |
| Partial update rollout | Failed/uncertain projects remain visible and later projects do not proceed implicitly |
| Model response without known ID or usage | No guessed lookup or resend; retain the reservation and show the limitation |
| Offline page or process eviction | Show stale data honestly; no queued mutation silently executes after reconnect |
| Restored unresolved work | Global quarantine blocks all effects; original intents and unresolved charges survive the audit |

Never manufacture a production failure merely to tick a box. If a condition
cannot be exercised safely within the approved trial, record **Cannot check yet**
and the prerequisite.

## Restore the project records

Follow the [workspace recovery procedure](web-recovery.md) first. Include worker
jobs/fences, update stages, model tasks/reservations, native retry requests and
their shared minute accounting in the private inventory. Reconcile provider
state independently from the snapshot. Missing post-snapshot operations remain
a coverage gap; no automatic replay or budget reset is authorized.

After global reopening, execution still requires a current feature restore
assertion. Its `restoreReconciledAt` must be a canonical past timestamp at or
after this restore's `recovery.startedAt`:

- Jobs, schedule writes and update preparation/publication use the jobs assertion.
- Model runs and checkpoint continuation use the model-routing assertion.
- Native night retries require both jobs and night-operation assertions.
- Night plan publication uses the night-operation assertion.

This allows a feature audit performed during quarantine to remain current.
The feature still needs its independent enabled setting, approvals, permissions,
source and budget checks. Recording a timestamp asserts an audit; it does not
perform it. Preserve the permanent recovery epoch and original backup. Inspecting
an original receipt after reopening does not require enabling new execution.

At the end of the agreed window, review repeated observations across projects.
Publish only a sanitized summary of what worked, what failed, what could not be
checked and what still needs a terminal. Keep the phase partial until its actual
operating outcome is demonstrated. Tests, a merged change and one successful
session do not establish lived-in usefulness.
